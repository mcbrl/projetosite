With the modernization of resources and the popularization of Cloud Computing, IT companies have realized the importance and advantages of adapting to these new models of provisioning, management, and consumption. Serverless is one of the models that is proving very popular with IT professionals.

These changes allowed companies to rely on cloud computing and storage resources, rather than just private data centers. We named this first generation of cloud infrastructure resources **IaaS** ( *Infrastructure as a Service* ).

Today we have access to a variety of high-level resources to support the development and delivery of applications, where we can even abstract the provisioning and scaling of infrastructure resources. We have named this new generation of resources *Serverless Computing* . Continue reading this article to learn about Serverless and its applications.

## Discover Serverless Computing

*Serverless Computing, or "computing without a server,"* is a relatively new concept and still lacks consensus in the industry.

Serverless Computing is both a model for software development and delivery, and for provisioning computing resources.

It is possible to clearly identify at least three dominant types of *serverless* computing :

- BaaS (*Backend as a Service*),
- FaaS (*Function as a Service*),
- Serverless Containers.

## Serverless “BaaS”

Software can now be developed using a multitude of resources available in the cloud as *services* . This greatly simplifies the programming process. The consumption of these various services can be integrated into a single software program with just a few lines of code and minimal configuration. This makes building secure solutions with very little complexity trivial.

Examples of "BaaS" ( *Backend as a Service* ) resources:

- Databases (Amazon RDS)
- API Gateways (Mulesoft)
- Authentication (Google OAuth)
- Blockchain (Ethereum)

In this model, the provisioning and management of these services are fully automatic and invisible to the developer using them in their applications.

## Serverless “FaaS”

The FaaS ( *Function as a Service* ) model consists of a simplified form of code development and packaging/delivery that is extremely trivial for the developer. The way in which computing resources will be provisioned to execute this code, when requested, is entirely abstract for the developer.

In FaaS ( *Function as a* Service), all the work is done by cloud providers who instantiate resources where and when they are needed, releasing them when they are no longer needed. The servers that run the developed code are *ephemeral* (disposable), and the technology used for its packaging, distribution, and provisioning is typically proprietary.

The interesting thing about the FaaS model is that it allows for billing models based on the consumption of computing resources. In this way, a *function* is only charged when it is activated. Therefore, since *functions* are inherently elastic, these resources will be provisioned on a larger scale during peak consumption periods.

## Serverless Containers

Docker is a platform that helps in the creation and development of isolated environments called containers. Containers are inherently portable and potentially easy to scale.

Docker allows you to package a self-contained environment for running software within containers, making it portable and compatible with any cloud provider.

Constant modifications to the environments are not necessary for the software to function correctly. The reason for the popularity of containers is that they have a small initial learning curve and translate into quick benefits. This is even good for deployments in private data centers. In fact, containerization has proven to be a very effective and low-cost strategy for migrating data centers to the cloud.

Since Docker is compatible with both Linux and Windows servers, its benefits are tangible for virtually any programming language or platform.

Their inherent portability and predictable behavior make containers a fundamental ally for the deployment of DevOps tools, culture, and processes. In fact, there are exceptional adoption strategies and tools that assume software projects use containers as tools for building, testing, and delivery.

Containers also work in hybrid environments (public and private clouds) and across multiple platforms, making it possible to manage environments that span multiple clouds ( *multi-cloud* ).

Several cloud providers have responded to the great popularity of containers by offering container orchestration in various provisioning and billing models (which we could call **CaaS** – *Containers as a Service* ). Currently, virtually all of them offer some proprietary way to publish containers (such as Amazon ECS), but there is a noticeable consolidation around container offerings managed by the most widespread orchestrator, Kubernetes.

A new generation of cloud provider-managed Kubernetes cluster offerings is emerging *.* These new offerings implement a strategy where servers are provisioned and disposed of based on demand. We can clearly call this model *Serverless* *Containers* . Notable examples of *Serverless Container platforms are Amazon's* **Fargate** and **Fargate** EKS offerings.

**Migration to using new technologies**

For a company to transition to the use of disruptive and high-impact productivity technologies (such as various *serverless approaches), IT teams need to prepare for the new changes. This is because traditional IT is usually sized and designed based on roles that will be transformed, both by the adoption of* *serverless* infrastructure models and by development and delivery models known as DevOps.

## **Advantages provided by using Serverless Computing**

The **reduction in operational costs** and lower management complexity are quite evident, with no need to pay for resources beyond those actually used. This reality holds true both when compared to private data centers and the more traditional Cloud Computing (IaaS) model.

Another advantage lies in the **reduction of the cost of scale.** *Automatic scaling* eliminates the need for manual intervention to meet peak demand.

Its use also simplifies software delivery, as less expertise is required for delivery (especially in the FaaS model). This translates into **reduced development costs**.

Adopting the Serverless model allows for better utilization of IT professionals, freeing them from unproductive tasks and reducing the potential problem area. Typical infrastructure skills remain necessary for projects (such as monitoring, security, and troubleshooting), but the operational silos of traditional IT need to be reinvented.

## **Advantages of Serverless Containers (Docker/Kubernetes)**

The container-based development and delivery model is extremely popular and successful, already enjoying great maturity and practical use throughout the software production chain. This ranges from provisioning tools on the development workstation to delivering software in production clusters.

Containers are inherently portable – choosing this delivery model means no lock-in with cloud providers. The FaaS model, on the other hand, implies a commitment to proprietary tools.

Note that, in practice, under the hood, all FaaS implementations are container-based. The degree of lock-in with a vendor depends on the dependency of the tools in the workflow and other provider resources being used (remember BaaS).

Serverless, container-based approaches offer sufficient simplicity and greater maturity to handle day-to-day challenges, especially when things don't behave as expected. The problem is that there are plenty of people who will claim otherwise.

This is a very heated arena at the moment, yet it's clear that this is a battle between cloud providers to promote maximum customer engagement with their platforms. The choices for each project must weigh productivity, cost, and future strategy.

## **Signing Off**

A more complex system may consist of a mix of BaaS, FaaS, and Serverless Containers resources. This means that the issue of lock-in is quite subtle and its relevance will have to be highly contextual. For example: Dependence on Amazon RDS for MySQL databases is not very relevant (any provider offers a compatible service), but depending on the Google Cloud Machine Learning Engine (Tensorflow) creates a greater commitment.

Therefore, there is no question of a serverless approach being better or worse. The issue of lock-in can be completely irrelevant in some cases or mortally crucial in others.

A more intangible value that is often ignored by traditional IT is "time-to-market" (time to launch a product) and continuous experimentation (such as the ease of experimenting with new technologies). The ease of incorporating components in the form of auxiliary containers or BaaS services from the cloud provider is essential for creating solutions that would otherwise be unfeasible. Not everything can be solved with new lines of code!
