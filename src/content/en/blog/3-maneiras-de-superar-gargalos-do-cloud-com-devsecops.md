You already know that [**DevSecOps**](/en/devsecops/) means thinking about application infrastructure and security from the very beginning of the build, and also automating the creation and checking of certain security ports, preventing the DevOps workflow from declining.

However, in parallel with the development of DevSecOps processes, the issue of cloud security ended up being left behind as a result. from a rapidly evolving infrastructure, as well as processes and tools that support DevOps and security individually, but not collectively.  
As a result, significant bottlenecks have been created that no single tool or technology can eliminate. 

However, we are here to share some of the existing methodologies for effectively implementing cloud-native security. Follow this new article and see what they are.

## 1\. Automate everything 

You're probably automating your cloud security, just like you did with your software testing. After all, it's completely unrealistic to expect even the best and most experienced security experts to always be up-to-date on best practices for every cloud provider, service layer, orchestration platform, feature, etc. Therefore, automation is the only way to do this comprehensively, without wasting time and resources.
However, this automation can end up creating more problems, because without actionable feedback, automating problem identification will only result in more work or, at least, more tickets that may or may not turn into scheduled work.
Given this scenario, finding the right tool to automate problem identification is crucial, but applying the same methodology to fix problems is even better. In other words, your goal should be to automate in order to prevent problems from occurring, not simply to identify them.

## 2\. Prevention is better than cure. 

Many DevSecOps problems stem from a historically reactive security mindset, which aims to protect against external threats rather than prevent them internally. And this is absolutely true when we talk about cloud security.
Now, with the emergence of [Infrastructure provisioning as code](/en/Infrastructure-as-code%3A-a-competitive-advantage-in-retail./)We can begin to shift this mindset toward a preventative approach that will not only put consistent protections in place, but also strengthen the infrastructure over time and save resources in the long run, as it prevents incorrect configurations from being deployed.
However, to do this, policies need to be translated, applied, and delivered in code. In other words, governance automation needs to be translated into a common language, and security professionals and DevOps engineers need to be equipped with actionable solutions. 
Applying policies at the code layer ensures that cloud security is performed consistently and allows it to scale across the environment over time, alleviating DevSecOps bottlenecks in the cloud.

## 3- Enhance your existing processes

The only way to make DevSecOps in the cloud accessible and readily adopted is to incorporate it into the tools and processes that developers rely on and use every day. 
While there's no one-size-fits-all solution for all organizations, performing automated checks on every code review is a great way to leverage existing workflows to encourage cloud DevSecOps adoption. This allows you to manage policies from within your CI/CD pipeline or provide feedback on... *commits* e *pull requests* It's a great way to set boundaries and provide actionable feedback.
The way you use this feedback will depend on the maturity of your cloud DevSecOps. In an ideal world, misconfigured infrastructure code is blocked before being merged into the central repository, and you have loops to quickly implement fixes before deployment – ​​much like what you probably already do when your integration tests fail on a build.

## Conclusion

When you automate, deliver, and integrate DevSecOps into the developer workflow, you make cloud security accessible to those who have the greatest impact on it, thus keeping your DevOps processes moving at full speed.
