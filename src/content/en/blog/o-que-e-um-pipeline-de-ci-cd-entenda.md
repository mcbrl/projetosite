At the heart of every successful DevOps workflow is the continuous integration and continuous delivery method, popularly known by the acronym CI/CD. Delivering applications frequently to customers is one of the premises of the [DevOps culture](/en/Discover-the-difference-between-DevOps--DevSecOps--and-NetOps./) , which makes software testing and delivery more stable and agile.

A CI/CD pipeline represents a chain of steps that are performed until the final version of a software is released. In this context, increasingly larger teams are involved in robust projects, and organizing the workflow is becoming increasingly necessary.

But you still don't know what a CI/CD pipeline is? No problem, read this article and see how it can change the way you look at your work methods.

## Continuous integration and continuous delivery: how does it work?

The CI/CD pipeline involves both monitoring and automation that are responsible for optimizing the application development process, including the initial testing phases, as well as the delivery and deployment stages.

To ensure this is done effectively, continuous integration and [continuous delivery](/en/benefits-of-having-a-continuous-delivery-conveyor-belt/) (CI/CD) pipelines are defined, which consists of the practice of accelerating software delivery.

## Stages and processes of the CI/CD pipeline

The CI/CD pipeline is divided into stages with distinct tasks. Let's look at a fairly common step-by-step process in projects.

When a developer writes their code, it's necessary to perform basic unit tests. Then, the responsible programmer can validate what was written and insert everything into the pipeline.

Therefore, the first processing element within the pipeline is the automated unit test, which includes tests for each component. Upon completion of this step, the pipeline performs the commit of this code to the repository.

Continuous integration begins here, as the *pull request* is created automatically and the controlled build is formulated. In parallel with the *Gated Builds* , the pipeline performs other unit tests and scans the code.

At this stage, the code becomes visible to other developers, which reduces the chances of inconsistencies in the code.

After completing all the previous steps, the *pull request* is validated, *peer reviews* are performed, and continuous integration is established. The pipeline switches to continuous delivery mode, and tests are conducted to verify that the program's critical functionalities are working sequentially in the QA and Dev environments.

The environment responsible for application quality is also tested through automated regression, making it possible to locate any additional defects or critical failures.

The final steps in the CI/CD pipeline include architecting the code and authorizing it with the production environment.

The entire process was automated; the programmer only needed to develop the code to meet the application's requirements, and the subsequent process was carried out safely, predictably, and quickly.
